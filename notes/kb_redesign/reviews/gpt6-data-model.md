# 2 Problems (ranked)

The following are architectural causes with additional executable counterexamples. Severity labels describe the demonstrated consequence: **blocks correctness**, **silently wrong**, **costs time**, or **cosmetic**. No cosmetic-only item is ranked here. Frequency means the triggering condition observed in a probe; no population failure rate is inferred.

**1. No serialized transaction or coherent read boundary — blocks correctness.** A controlled interleaving of two real public knowledge appends makes both read the same prior head: both return success, sequences become `[1,2,2]`, and chain verification fails at row index 2. A two-result batch retains its first append when the second verifier fails. Separately, one legal append between dashboard reads yields history `[T::old]` but current nodes `[T::old,T::new]`; the new node has no displayed history although chain verification succeeds. Trigger: overlapping writers, failed batch prefixes or writes between related reads; no production incidence was measured. Root design: sequence allocation, dependency validation, hash append, CSV regeneration and each consumer's reads are independent operations. [knowledge_database.py:209](/data/haiyangw/harness/Chandra/_common/ledgers/knowledge_database.py:209), [ledger_common.py:134](/data/haiyangw/harness/Chandra/_common/ledgers/ledger_common.py:134), [result_database.py:159](/data/haiyangw/harness/Chandra/_common/ledgers/result_database.py:159), [dashboard.py:209](/data/haiyangw/harness/Chandra/_common/visualization/dashboard.py:209). [Writer/batch receipts](/tmp/chandra/kb-analysis/data/ledger-experiments/run-01/results.json), [snapshot counterexample](/tmp/chandra/kb-analysis/data/runtime-audit/logs/scenarios-python.jsonl).

**2. References bind mutable names, not the proposition/version admitted — silently wrong.** Reusing one result ID for an unrelated proposition in the same paper leaves the old claim admitted and pointing to the new current meaning; history contains both rows. An obligation can become a claim under the same entry ID. Equal result IDs in different papers are legal independent entities and must both survive migration. Trigger: an ID is reused or a referenced entity changes meaning/kind. Root design: last-row maps collapse entity, revision and event identity, with no immutable type or version-targeted reference. [result_database.py:187](/data/haiyangw/harness/Chandra/_common/ledgers/result_database.py:187), [claims_database.py:218](/data/haiyangw/harness/Chandra/_common/ledgers/claims_database.py:218). [Identity scenarios](/tmp/chandra/kb-analysis/data/ledger-experiments/run-01/results.json). Explicit metadata corrections can preserve scientific identity; correction/retraction of the proposition must declare its support consequences.

**3. Historical admission is treated as current support after refutation — silently wrong.** Checked result→refuted leaves its claim admitted and obligation discharged; a fresh admitted claim correctly fails, but a fresh discharged obligation citing that refuted result succeeds. Solid A→solid B, then A→blocking, still allows a new solid C depending on B; the runtime offers C as ready. All histories remain hash-valid. Trigger: refutation, demotion or reduction-reference retyping after settlement. Root design: existence/immediate-status checks occur only at append, with no reverse support lifecycle or effective-validity reducer. [claims_database.py:142](/data/haiyangw/harness/Chandra/_common/ledgers/claims_database.py:142), [claims_database.py:155](/data/haiyangw/harness/Chandra/_common/ledgers/claims_database.py:155), [admission.py:291](/data/haiyangw/harness/Chandra/_common/ledgers/admission.py:291), [dag.ts:66](/data/haiyangw/harness/Chandra/orchestrator/src/dag.ts:66). [Lifecycle receipts](/tmp/chandra/kb-analysis/data/ledger-experiments/run-01/results.json), [runtime readiness](/tmp/chandra/kb-analysis/data/runtime-audit/logs/scenarios-node.jsonl). This is a new temporal counterexample beyond the known readiness symptom; the nonblocking sample backlog is not evidence of incorrect closure.

**4. Relation typing and waiver provenance stop at the immediate row — silently wrong.** An explicitly waived missing ancestor carries `allow_missing_deps`, but its solid child and checked result admit with no inherited flag. Missing plain-string and typed-object dependencies also admit. A checked artifact-backed `skip_exec` row preserves the flag in raw history while result Markdown/state omit it. Trigger: escaped support, non-namespaced/object dependencies, or ordinary rendered consumption of a waiver. Root design: array/string heuristics replace a typed relation contract, and views do not derive inherited support constraints. [admission.py:255](/data/haiyangw/harness/Chandra/_common/ledgers/admission.py:255), [admission.py:291](/data/haiyangw/harness/Chandra/_common/ledgers/admission.py:291), [result_database.py:335](/data/haiyangw/harness/Chandra/_common/ledgers/result_database.py:335). [Exact dependency/provenance probes](/tmp/chandra/kb-analysis/data/ledger-experiments/run-01/results.json). Explicit escapes remain possible but must remain visible in derived closure and descendants.

**5. Paper partition and global graph scope disagree — blocks correctness.** Duplicate exact node ID `shared::n` in papers P/Q can be solid/hypothesis; hints P/Q/R resolve solid/hypothesis/solid, and equivalent child gates succeed/fail by hint. In a three-paper chain, transitive query returns one of two ancestors; runtime Q reports no ready node when its predecessor is solid in P, while direct admission accepts it. Trigger: duplicate global-looking names or cross-paper dependencies; neither occurs in the self sample. Root design: hinted-first admission lookup, paper-local traversal and paper-local readiness implement incompatible graph scopes. [admission.py:185](/data/haiyangw/harness/Chandra/_common/ledgers/admission.py:185), [knowledge_database.py:328](/data/haiyangw/harness/Chandra/_common/ledgers/knowledge_database.py:328), [dag.ts:16](/data/haiyangw/harness/Chandra/orchestrator/src/dag.ts:16). This extends known alias symptoms into ownership and resolution; no automatic alias/fuzzy merge is justified.

**6. Admission never validates the proposed global DAG — blocks correctness.** Reappend an existing solid root with itself as predecessor: solid self-loop accepted. Admit solid P::a, then Q::b depending on it, then revise P::a to depend on Q::b: both remain solid, no bypass flag, valid hash chains. Trigger: updates that close dependency cycles; both explicit scenarios reproduce. Root design: checking the old graph's immediate predecessor status cannot establish acyclicity of the proposed graph. [admission.py:283](/data/haiyangw/harness/Chandra/_common/ledgers/admission.py:283). [Graph counterexamples](/tmp/chandra/kb-analysis/data/ledger-experiments/run-01/results.json). The existing runtime cycle fixture does not gate public appends; dependency/supersession cycles need rejection, while ordinary citations may cycle.

**7. **B — canonical accepted-transaction JSONL log plus rebuildable SQLite.** Keep four public domain row APIs but make them adapters to one accepted-transaction boundary. Original four streams become immutable archives, referenced by genesis manifests containing exact full-file digests, byte/line locators, counts, last hashes and unhashed-prefix information. Preserve malformed, ambiguous and unhashed records as legacy observations with explicit import/trust status and historical admission-policy identity; unknown policy remains unknown. Preserve each stream's order without inventing historical global chronology. Uncertain links cannot silently settle current work. New one-line hash-chained transaction envelopes contain related logical events with unique transaction/event/version IDs, producer idempotency key, expected input versions, actor role, run/evidence references and generated observations. “Accepted” means accepted into canonical memory: a result may still be unchecked/refuted, and a failed scientific attempt can be an admitted trial event.

SQLite is a derived projection: entities, versions, events, typed edges, evidence, verifier runs, current/effective state and FTS documents; it stores its last applied sequence/hash. `paper` is an association/property; legacy compound identities are preserved in mappings. Sources and skills remain in their existing canonical systems unless explicitly admitted by a later extension; their references can be indexed without making them new authoritative graph nodes. The index is untracked and disposable. All queries, runtime gates and views use the same reducer/projection and declared committed head; no alternate unchecked reader remains.

The write protocol is explicit:

1. Check the stable idempotency key before rerunning a verifier: the same canonical request returns its original transaction, while a changed payload conflicts. Capture a committed input snapshot and retain immutable input/code/config/evidence bytes. Run verification outside the writer lock, recording actual command, environment policy, source revision/dirty diff and outputs. Pin event-schema, admission-policy and reducer versions.
2. Acquire the single writer lock; recheck the key, current head, expected support/evidence versions, transitive current validity and proposed typed graph/settlement constraints. Recheck retained artifact bytes. A changed prerequisite rejects/retries the proposal; an old verification does not certify new inputs. Typed scope/evidence policy selects the applicable executable verifier; SQL constraints cannot determine scientific sufficiency.
3. Append and fsync one accepted transaction envelope; fsync its directory on creation/rotation before acknowledging. Only durable complete envelopes are canonical. After recovery, a surviving valid complete envelope is committed even if its acknowledgment was lost. Exactly-once accepted events do not promise exactly-once verifier execution; retries must handle that distinction explicitly.
4. Catch up the index in a SQLite **write transaction**, advancing projected rows and sequence/hash atomically, then pin a **read transaction** and return its actual head. Default requested head means a minimum ancestor: reject unknown/non-ancestor heads and return the actual pinned descendant head. Exact as-of queries require version/temporal filtering; current tables at H2 cannot answer exact H1. Incomplete/corrupt replay fails closed. Responses use bounded projections and page history/details under the pinned head, avoiding whole-history bridge payloads.
5. Retain rejected proposals and corrupt/torn bytes as incident evidence. Explicit recovery identifies prior valid head/byte offset and the entire damaged-segment digest, then binds a new segment to that record; never silently skip holes or truncate admitted history. A committed write receipt remains valid if projection catch-up needs recovery. SQLite is never an alternative canonical commit.

B invariants include all A identity/support/evidence rules plus version-pinned deterministic reducers, atomic envelope acceptance and exact projection/log cursor agreement. Transactional SQLite alone does not make a separate JSONL append atomic. A full rebuild must reproduce entity versions, typed edges, historical reported states, effective validity, views and FTS documents at the same committed head. Metadata-only replacement need not invalidate an immutable scientific version; explicit correction/retraction must mark affected support stale/invalid while retaining original gate history. A trusted retained head detects local rollback relative to that head; full-repository rewrite resistance needs a separately trusted Git head or stronger checkpoint, not a manifest rewritten beside the log.

# 4 Recommendation

Adopt **emergency A protections, then staged B**, conditional on the acceptance gates below. Begin with one authoritative reader/writer boundary, declared storage homes, integrity diagnostics and serialized append/replay behavior. Those are needed before more parallel work regardless of eventual storage choice. Avoid a standalone performance-only SQLite migration that preserves inconsistent reducers and unversioned support.

B fits the existing four domain APIs and Python bridge while making events, versions and typed relations explicit. Its index supplies complete cross-ledger queries, reverse support lookup, lifecycle/retrieval views and a common committed snapshot. It can add FTS without claiming semantic similarity or scientific equivalence. C should wait until canonical source/evidence/skill graph authoring has demonstrated benefits that justify changing every producer contract.

**What would not change:** append-only hash history; executable admission; evidence classes and provisional statuses; generated views; ledgers as the research record instead of prose; immutable source mirrors and large data outside Git; delegated roles and the commit gate; distinct claim, result, task and trial concepts. There is no requirement to adopt a vector index, graph database product or semantic deduplication. B already has typed relational edges; C adds a universal canonical ontology and authoring/query contract.

Preserve original reported statuses and verifier outcomes. Compute effective current validity from explicit support-version edges, evidence availability and inherited waivers; expose both everywhere. Obligations need declared mission/backlog scope, affected entities, expected evidence class and settling relationship. A simulation obligation can be discharged by appropriate simulation evidence; there is no universal exact-proof gate. New support loss creates visible invalidation/review work rather than rewriting old admissions.

Acceptance is correctness first: byte/ID/hash preservation, no acknowledged lost/duplicate transaction, no mixed snapshot, reproducible projection, correct cross-paper traversal, rejected cyclic updates, no silent proposition rebinding, visible stale support, retained evidence and exact attempt accounting. Measure latency again after semantic parity; current synthetic timings must not be extrapolated into production rates or a promised speedup. Supported initial durability is one writer on a tested local filesystem; Git branch divergence needs explicit reconciliation instead of concatenating independent chains.

# 7 Open questions for owner

These are remaining policy choices for implementation, not permission requests or reasons to leave the analysis incomplete. Recommended defaults are stated so migration can be planned concretely.

1. Which existing obligations are mission-critical versus project backlog, and which evidence class/scope settles each? Default: preserve existing `blocking=false` as reported history; add explicit scope prospectively, never infer criticality from an open status alone.
2. What changes preserve an entity's proposition, and what requires a new entity plus `supersedes`? Default: immutable entity kind, explicit versioned correction, and owner adjudication for unrelated statements/ambiguous historical IDs.
3. Where is the independently trusted genesis/head checkpoint retained, and what threat model should checkpointing and role isolation cover? Default: preserve a known trusted source commit plus exported full-file manifest; same-directory hashes are not whole-repository attacker resistance, and role-gated subprocesses are not host-file isolation.
4. What retention policy applies to evidence too large for Git, unavailable historical artifacts and sensitive verifier outputs? Default: content-addressed external artifact retention with durable digests/availability status; never fabricate missing bytes or silently upgrade evidence.
5. What defines the same research approach across task renames, and which verified event resets a failed approach? Default: explicit stable approach/attempt IDs, failure cause plus scope, and a recorded structural pivot; retrying a transaction is not a new experiment.
6. Is one writer on a supported local filesystem sufficient, or must independent machines/branches admit concurrently? Default: single local writer with explicit Git divergence reconciliation; a distributed commit protocol is outside the estimated B scope.

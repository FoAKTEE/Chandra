# commit-gated — verify one node, check its message, then commit

## When to use

- Land a verified DAG node or a finer substage within that node.
- Repair a commit-message rejection or select a research/process commit type.
- Install the tracked commit hook in a clone where commits are authorized.

## Steps

1. Read `AGENTS.md`, `_common/contracts/commit_template.md`, and the Commit cadence
   section of `_common/contracts/progress_principles.md`.
   Follow the binding policy: **ONE COMMIT PER DAG NODE (or finer)**.
   Commit tests before or with the code they verify; never defer tests to a later commit.
   If working under a no-commit worker assignment, deliver the diff and tested message
   to the landing owner instead of staging or committing.
2. Activate the hook once per authorized clone:
   ```bash
   bash _common/hooks/install.sh
   git config --get core.hooksPath
   git config --get commit.template
   ```
   The installer sets the hook path to `_common/hooks` and, when present, the template
   to `.gitmessage`. Installation changes clone configuration; the Verify block below
   tests the hook standalone without installing it.
3. Delimit the node's artifact set and run its actual verifier before writing a success
   claim. Include its evidence/tolerance and measured output. A passing message hook
   checks message syntax; it does not admit research evidence or inspect commit scope.
   Keep large datasets, binaries, rendered HTML views, and source mirrors out of git.
   Store data/mirrors under gitignored `ref-paper/`, `ref-code/`, or outside the repo;
   keep source provenance and reproducible generators rather than bulky outputs.
   Keep run scratch outside the repo as specified by `INDEX.md`.
4. Choose exactly one primary type by intent:

   | Trigger | Type |
   |---|---|
   | Correct wrong output/behavior | `fix` |
   | Add a capability, solver, figure generator, or reproducible artifact | `feat` |
   | Speed up while preserving results | `perf` |
   | Restructure without changing behavior | `refactor` |
   | Undo a prior change | `revert` |
   | Change shared methodology, pipeline, schema, hook, or infrastructure | `infra` |
   | Launch, continue, or record a compute run; outcome judged later | `exp` |
   | Record investigation, root cause, disproof, measurement, or reframe | `diag` |
   | Record a methodology decision, convention, or proof sketch | `notes` |
   | Write other documentation/status/checkpoints | `docs` |
   | Confirm behavior with tests rather than discover a finding | `test` |
   | Housekeeping / build / CI / formatting | `chore` / `build` / `ci` / `style` |

   For mixed work within one node use the most consequential action:
   `fix/feat > diag > exp > infra/docs/chore`. Put secondary actions in body objects.
   Split different nodes instead of using this tie-break to bundle them.
5. Write the title as `type(scope)[!]: imperative summary`. Scope is optional;
   use narrow identifiers, optionally comma-separated with no spaces.
   Keep the type at column 1, target about 72 characters, and omit a trailing period.
   Place iteration/window numbers in footers, never before the type.
   The hook's regex accepts the listed types and nonempty scopes/summaries; it does
   not enforce imperative wording or lowercase scopes and warns on length only above 100.
6. After a blank line, write optional typed body objects in this usual order:
   `why`, `finding`, `change`, `run`, `result`, `verify`, `caveat`, `next`, `files`.
   Put one `- kind: ...` per top-level line; indent continuations under that object.
   Tag every `finding` and `result`: `[SOLID]` verified/reproducible,
   `[PRELIMINARY]` indicative, `[HOLE]` unresolved, or `[FUTURE]` deliberately deferred.
   In `verify`, name the command, evidence modality, verdict, and observed output.
   A subject-only message is legal, but it cannot substitute for evidence of completion.
7. Pair `!` and a `BREAKING CHANGE:` footer **iff** the change invalidates a committed
   result/claim or a default affecting published output. Name exactly what is invalidated.
   Use other footers only as needed: `Iter:` OR `Window:`, `Run:`, `Refs:`, `Verify:`, `Claim:`.
   Include no tool/model attribution of any kind: no "generated by" text and no
   co-author trailers naming an AI. The hook does not enforce this policy; inspect manually.
8. Write the exact message to a temporary file; replace the placeholders before landing:
   ```text
   infra(<scope>): <imperative change>

   - change: <node-scoped source and test changes>
   - result: <measured outcome, with its actual evidence level> [SOLID]
   - verify: <exact command; modality; verdict; verbatim output>
   - caveat: <remaining limitation, if any>

   Refs: <node ID and evidence anchor>
   ```
   Test a nonempty message file explicitly; a missing or empty file can exit 0 because
   the hook leaves those cases to git. Set `message_file` to the prepared file:
   ```bash
   test -s "$message_file"
   COMMIT_GATE_STRICT=1 _common/hooks/commit-msg "$message_file"
   ```
   Default mode hard-rejects invalid titles and warns on checked body/tag/footer issues.
   `COMMIT_GATE_STRICT=1` makes every warning fatal. Repair failures; do not bypass the gate.
9. If authorized to land, stage only this node's files, inspect the complete staged diff
   and file sizes, and confirm tests and no bulky/attribution artifacts are included:
   ```bash
   git add -- '<node-file>' '<test-file>'
   git diff --cached --stat
   git diff --cached
   COMMIT_GATE_STRICT=1 git commit --file "$message_file"
   ```
   The cadence prose describes packet/wave commits; `orchestrator/src/gitops.ts`
   currently stages all changes and writes an untagged result object, which strict mode
   rejects. Neither behavior supersedes the one-node policy. Supply a compliant,
   scoped landing rather than relying on that runtime message as a template.

## Verify

```bash
set -euo pipefail
bash -n _common/hooks/install.sh
test -x _common/hooks/commit-msg
scratch=$(mktemp -d /tmp/chandra-commit-skill.XXXXXX)
trap 'rm -rf "$scratch"' EXIT
cat > "$scratch/good" <<'MSG'
infra(hooks)!: exercise standalone message admission

- finding: this fixture describes a classified claim [PRELIMINARY]
- change: replace an earlier message fixture
- verify: standalone commit-msg fixture check

BREAKING CHANGE: invalidate the earlier fixture default
MSG
COMMIT_GATE_STRICT=1 _common/hooks/commit-msg "$scratch/good"
reject() {
  if COMMIT_GATE_STRICT=1 _common/hooks/commit-msg "$scratch/bad" > "$scratch/output" 2>&1; then
    echo 'expected commit-msg rejection' >&2
    return 1
  else
    test "$?" -eq 1
  fi
}
printf '%s\n' 'invalid title' > "$scratch/bad"
reject
printf '%s\n' 'diag(hooks): exercise missing tag' '' '- finding: untagged fixture' > "$scratch/bad"
reject
printf '%s\n' 'fix(hooks)!: exercise missing footer' > "$scratch/bad"
reject
```

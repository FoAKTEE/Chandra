# gotree：用 LLM 做树搜索和分层记忆，目标是复现 AlphaGo 第 37 手

任务说明的精简版见 [docs/PROMPT.md](docs/PROMPT.md)。本文说明设计：每个问题先列出可选方案，再说明默认选哪个、为什么。所有默认值都可以通过 `--set KEY=VALUE` 修改。

## 0. 几个判断

1. **目标手。**"神之一手"指 AlphaGo 对李世石第二局的第 37 手，黑棋 P10 五路肩冲。棋谱已放在 `data/alphago-leesedol-2016-g2.sgf`，代码已核对第 37 手确实是 `B[oj]` = P10。第四局第 78 手 L11 是李世石的"神之一手"，作为第二个测试局面。
2. **这一手在现代引擎眼里的位置。**用仓库自带的小网络（b10c128，800 visits）离线评测：引擎首选 D13，P10 在引擎排名里第 4 到 5 位（两次运行），损失约 0.8 目，策略先验排第 4。所以"复现"应定义为"找到 P10，或者找到一手同样好的棋"。只看是否下出 P10 太苛刻，也不符合围棋本身的事实。换成强网络后需要重测。
3. **自博弈不能自动保证复现。**UCT 收敛到最优解有两个前提：无限次访问，以及终局值精确。实际所需预算取决于 LLM 估值和候选点的质量。当年第 37 手在人类策略网络里的先验大约只有万分之一。所以本设计在三处刻意加了强制广度：非常规候选配额、区域侦察、根节点最少访问次数。同时提供两个便宜的前置测量：`prior`（会不会被提出来）和 `judge-values`（估值准不准），先测再花钱。
4. **为什么 LLM 有可能做到。**Graepel 对 LLM 的批评有两点：没有显式的认知状态，没有搜索。DAG 就是显式的认知状态，可以审计、可以复用；代码调度的 PUCT 就是搜索。LLM 在其中只承担 AlphaGo 两个网络的角色。这也是 Heuristic Learning 的思路：经验以显式、可读、可删改的形式存放，而不是存在权重里。

## 1. 架构

```
           ┌──────────────── orchestrator（代码，单写者）────────────────┐
 实际对局 ──► 根局面 ──► 选择(PUCT/加宽/根广度) ──► 任务 ──► 结果校验 ──► 回传/写 DAG
 (arena)       ▲                                     │
               │                         ┌───────────┴─────────────┐
       KataGo 回一手后                   │  worker：每个任务一个新会话 │
       新根 = DAG 中已有节点             │  claude -p / codex exec /  │
       （子树复用，换位共享）            │  API / mock；工具 gtree：  │
                                         │  card try window ladder    │
                                         │  known lessons submit      │
                                         └───────────┬─────────────┘
   L0 局面 DAG (dag.db) ◄── 每个任务的结果、worker 自己读的变化（gtree try）
   L1 棋形教训 / L2 概念 DAG (memory.db) ◄── 决策后的 abstract 任务、consolidate
   L3 代码启发式 (user_heuristics.py) ◄── HL 循环 (heurtest)
   离线裁判 (judge/，KataGo) ── 只读 DAG，只写自己的目录，绝不回流
```

## 2. 局面的数据形式

| 方案 | 内容 | 问题 |
|---|---|---|
| A 原始 ASCII 棋盘 | 一张图 | LLM 在 19 路上数气、对齐坐标都容易出错 |
| B 坐标列表 | 黑子、白子各一串坐标 | 没有空间结构 |
| **C Position Card（默认）** | 见下 | token 多一些（每张约 2–3k） |
| D 渲染成图片 | 多模态 | 可作为附加项，待评测 |

**存储格式（冻结局面）**是 `Position(size, cells, to_play, ko, passes, komi)`：`cells` 是长度 N² 的 `.XO` 字符串。手顺和提子数不属于局面身份，因为数子规则下它们不影响后续。这正是需求里说的"冻结形式"。

节点的键是 8 种对称变换下字典序最小的那个形式再取哈希，所以换位和对称局面会合并成一个节点。边上的着法记在父节点的规范坐标系里，子节点上记录它对应的对称变换编号，代码沿路径组合这些变换，就能还原到真实棋盘坐标。需要给人看时，可以导出为 SGF 摆子格式（`sgf_setup()`）。

**给 LLM 的 Position Card**（`perception.py`）包括：
- 四边都标坐标的棋盘，上一手加括号，劫点用 `#` 标出；
- 棋块表：按气数排序，列出叫吃（以及提子或逃跑的点）、两口气、征子能否成立、Benson 无条件活棋；
- 势力草图，并注明它不可全信；
- 局部放大窗口，通过 `gtree window` 查看。

做法和 AlphaGo 的输入特征平面一样：事实由代码算出来，判断交给 LLM。

## 3. 记忆：树和 DAG 的分层

| 层 | 内容 | 键 | 写入 | 读取 |
|---|---|---|---|---|
| L0 局面 DAG | 搜索的精确结果：N、W、先验、LLM 静态估值、理由 | 规范局面哈希 | 每个任务完成后 | 选择阶段；`gtree known` |
| L1 棋形教训 | "这种形里什么好、什么不好" | 以某点为中心的 7×7（精确）和 5×5（模糊）局部图样，颜色相对、对称规范化 | 每次决策后的 abstract 任务，只写"意外" | 每个任务按候选点检索，有字数预算 |
| L2 概念 DAG | 全局原则 | 泛化、细化、矛盾、例子四种边 | abstract 和 consolidate | 按阶段和棋盘大小检索 |
| L3 代码启发式 | 候选排序、快速估值 | 代码 | HL 循环（heurtest 加回归测试） | 搜索的默认先验、加宽时的候选池 |

**备选方案**：
- 只有文本笔记，也就是 Dojo 的 playbook，可作为对照组；
- 每个根局面一棵独立的树，没有换位共享，同一局面会被重复搜索；
- 只有 DAG、没有抽象层，结果无法迁移到别的局面。

**默认方案是 L0 到 L3 全部启用。**

**写入受"意外"门控。**只有当先验排名和搜索结果不一致时才值得写入：低先验的着法赢了，或高先验的着法被驳倒。这相当于用 TD 误差决定什么值得记住，记忆因此不会无限膨胀。教训文本里禁止写绝对坐标，只描述棋形，这样才能迁移到别的局面。

## 4. 长程思考与会话边界（对应需求中的"重置残局"）

| 方案 | 做法 | 评价 |
|---|---|---|
| A 一个长会话 + auto-compaction | Claude Code 的默认方式 | 上下文会腐化；象棋版 Astra 的退化疑似就是这个原因 |
| B 每一手开一个新会话 | 需求里的建议：给新会话一份基于 DAG 的简报 | 方向正确，但一个会话内部仍然要想很久，也无法并行 |
| **C 每个任务开一个新会话（默认）** | 粒度细化到"扩展这个节点""从这里自博弈 8 手"；所有状态都在 DAG 里 | 上下文有界，可大规模并行，可复现，任何会话都不需要压缩 |
| D agentic 模式 | 每一手只有一个长任务，由 Claude Code 用 `gtree try` 自己读棋，所有变化落进 DAG | 作为对照；用 `--budget 1 --job-timeout 3600` 即可实现 |

需求里观察到："LLM 下完一步、KataGo 也下完一步，就等于回到一个可以重置的残局。"方案 C 把这个观察推到最细的粒度：每个任务本身就是一个冻结残局上的一个小问题。走完一步棋后不需要恢复任何对话，新的根节点很可能已经在 DAG 里，因为上一手搜索时已经搜过对手的应手。

## 5. 搜索算法（`search.py`）

- **选择**：PUCT，Q 取自子节点（换位共享统计），探索项用边的访问数；有虚拟损失，支持多个 worker 并行。
- **扩展和估值**：一次 `expand` 任务同时返回候选点及先验（策略）和胜率（估值），相当于 AlphaGo 的联合网络。
- **渐进加宽**：一个节点准入的子节点数为 k0 + c·N^α；不够时发 `more` 任务要新的候选，并明确排除已有的着法。
- **根节点强制广度**，这是能否找到第 37 手的关键：
  1. 每次扩展都要求额外给出若干"人类第一眼会否定"的非常规候选；
  2. 9 个区域各侦察一次（"只看右边，这里最好的棋是什么"），保证不会漏掉整块区域，例如右边五路；
  3. 每个候选有最少访问次数：LLM 候选至少 2 次，非常规和侦察候选至少 1 次；
  4. 先验混入均匀噪声。
- **LLM 自博弈**：`rollout` 任务让 LLM 同时扮演双方，连下约 8 手，然后评估终点局面；整条线写进 DAG 并回传。用 `--worker-for rollout=codex:...` 可以让另一家模型来下，即需求里说的"LLM 之间的自博弈"。
- **worker 自己读的变化**：worker 用 `gtree try` 读过的变化会自动写进 DAG；如果附带了胜率估计，还会参与回传。
- **批评任务**：`refute` 任务专门攻击当前领先的着法，用来抵消 LLM 对自己下法过于乐观的倾向。
- **决策**：默认选访问数最多的着法。也可以 `decide=llm`，但要求 LLM 推翻搜索结果时必须给出具体的反驳。
- **提前停止**：领先着法已经不可能被追上时停止。
- **复用**：DAG 是持久的，下一手、下一盘、下一次探针都从已知内容开始；`--memory` 可以在多个 run 之间共享 L1 和 L2。

## 6. 沉淀与抽象：控制每一步的思考时长

1. **abstract 任务**：决策之后，把搜索摘要（包括其中的"意外"）交给 LLM，让它写出最多 4 条教训，并与已有教训建立关系。
2. **consolidate 任务**：定期合并重复教训，生成上位概念，标记矛盾，淘汰坏教训，由此形成概念 DAG（`python -m gotree consolidate`）。
3. **HL 代码蒸馏**：coding agent 按 `docs/prompts/hl-heuristics.md` 的要求，把高频判断写成 `user_heuristics.py`，用 `heurtest` 和训练/测试划分来验证。代码启发式越准，需要 LLM 出手的节点就越少，这正是"沉淀"的目的。
4. **检索预算**：每个任务的记忆简报有字数上限，每个任务的上下文也有上限，所以每一步的花费由 `--budget` 决定，而不是由模型想多久决定。

## 7. 评测

| 测什么 | 命令 | 说明 |
|---|---|---|
| 是否认得这盘棋（污染检查） | `probe` 第 0 阶段 | 局面以规范朝向呈现 |
| 先验覆盖 | `gotree prior --samples 10` | 最便宜，最先做 |
| LLM 估值质量 | `gotree judge-values` | 和 KataGo 的平均绝对误差、判断领先方的一致率；mock（势力草图）的基线约为 0.45，相当于随机 |
| 发现曲线 | `gotree probe` | 目标的排名和访问数随任务数的变化 |
| 决策质量 | `gotree judge` | 每次决策损失多少目、在引擎里排第几（离线） |
| 对局强度 | `runner --harness tree` | 在 9 路阶梯上的 Elo，和 Claude Code、Codex、Dojo 同场比较 |
| 泛化 | 待实现：从强引擎自博弈中挖"人类先验低、引擎首选"的局面 | 防止只靠一个名局下结论 |

**消融**：
- `--set root_scouts=false`
- `u_root=0`
- `rollout_frac=0`
- `refute_frac=0`
- `abstract=false`
- 只用代码启发式（`--worker mock`）
- 不同模型做 rollout

## 8. 路线图和继续投入的判断标准

| 阶段 | 内容 | 花费 | 继续的条件 |
|---|---|---|---|
| 0 | 每个模型跑 `prior` 和小预算 `probe`（约 50 个任务），再跑 `judge-values` | 低 | 有任一模型能提出 P10，或者估值与引擎的一致率明显高于 0.5 |
| 1 | 9 路 arena：tree harness 与 Claude Code、Codex、Dojo 比较 | 中 | tree harness 的 Elo 明显更高，说明搜索确实有用 |
| 2 | 第 37 手预算扫描：200 → 1000 → 5000 个任务，加消融 | 中到高 | 发现曲线随预算单调变好 |
| 3 | 泛化局面集，L3 代码蒸馏，共享记忆 | 高 | 在新局面上复现 |

## 9. 超算部署

- **arena 和 KataGo**：放在 GPU 节点，用 `scripts/slurm/arena.sbatch`；搜索任务放在 CPU 节点，用 `probe.sbatch` 或 `play.sbatch`。真正的瓶颈是 LLM API 的速率限制，而不是本地算力。`--workers` 的设置要和 API 配额匹配。
- **网络**：计算节点必须能访问模型 API（直连或经代理），claude 和 codex 需要事先登录，或者在环境变量里提供 key。
- **隔离**：worker 带 `--dangerously-skip-permissions` 运行，必须放进沙箱。用 `--wrap` 加前缀，例如：
  ```
  --wrap "bwrap --ro-bind / / --bind {jobdir} {jobdir} --tmpfs $PWD/judge --tmpfs $PWD/engines --dev /dev --proc /proc"
  ```
  这样 worker 只能写自己的任务目录，也看不到 KataGo 和裁判结果。
- **成本估计**（实测加估算）：19 路第 37 手局面的 expand 提示约 7.5k 字符（约 2–3k token）。每次 `gtree try` 再增加约 1.5k。Claude Code 每个会话还有固定的系统提示开销（可缓存）。粗略估计，每个任务 2–4 万输入 token（大部分命中缓存），加 2–8k 输出 token。2000 个任务的一次探针，约 4000 万到 8000 万输入 token、400 万到 1600 万输出 token。按这个量级，单个局面的探针可行，19 路整盘不可行。真实数字以 `usage` 字段为准，探针报告会汇总。

- **已验证（49 个自动测试加实跑；另有两轮独立代码审查，发现的 26 个问题已全部修复，并补了回归测试）**：

  - 完整的 Claude Code 任务目录协议（用假 CLI 测试：`gtree try` 和 `gtree submit`，包括校验失败后重新提交）；
  - API worker 的工具循环；
  - mock 下的第 37 手探针，以及 KataGo 离线裁判；

  - Codex 的输出解析只按文档格式实现，没有实跑。
